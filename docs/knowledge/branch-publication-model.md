# Branch Publication Model

Arbor separates authoring from publication.

The `source` branch is the only canonical authoring environment.
All human development, issues-to-code work, documentation source, release-note
source, workflow source, and pull requests target `source`.

`pre-release` and `release` are generated outputs built from `source`. They
present built project state to users and must not become places where humans
edit source, docs, wiki content, or release metadata.

Generated publication outputs include the public repository shape:

```text
.github/
content/
src/
README.md
CONTRIBUTING.md
CHANGELOG.md
LICENSE
```

Repository-facing files are generated from `content/repo/` and locale data,
then moved to the publication repo root. Localized wiki output is generated
from `content/pages/` and locale data. Release-note source does not publish
directly; generated branches receive `CHANGELOG.md` instead.

## Branch Roles

### `source`

`source` is the canonical authoring branch.

All implementation, documentation source, wiki source, localization source,
generation tooling, schemas, and validation tooling live here.

Human-authored pull requests target `source`.

### `pre-release`

`pre-release` is the generated pre-release view of the next release.

It exists so maintainers can inspect upcoming generated output before promoting
it to `release`.

Its history is disposable and may be regenerated by automation.

Human-authored pull requests should not target `pre-release`.

### `release`

`release` is the public stable publication branch.

It should be the repository's default public-facing branch once the publication
pipeline exists.

Its contents are generated from `source` and should never be treated as the
canonical source of truth.

Human-authored pull requests should not target `release`.

## Ownership

| Branch | Owner | Human editable |
| --- | --- | --- |
| `source` | Maintainers and approved contributors | Yes |
| `pre-release` | Automation | No |
| `release` | Automation | No |

Automation publishes. Humans author.

## Contribution Flow

1. Open an issue for discussion, bug reports, RFCs, translation requests, or
   feature proposals.
2. Reach agreement on the intended change.
3. Implement the change on `source`.
4. Submit a pull request targeting `source`.
5. After review and merge, automation generates `pre-release`.
6. After validation, automation promotes generated output to `release`.

## Generated Content

Generated branches are build outputs.

If generated content needs to change, edit the corresponding source on
`source`. Direct edits to generated branches are invalid and may be overwritten.

`CHANGELOG.md` is generated from the version-shaped `release-notes/` tree. It
is a publication view, not a source-branch owner. Generated publication
branches include `CHANGELOG.md` and exclude the source `release-notes/` tree.

Publication automation may generate `pre-release`, `release`, or both from a
validated `source` state. Stable publication and pre-release publication
should be independently runnable, but they should both consume source-owned
inputs rather than hand-authored publication branch changes.

The manual `Publish` workflow accepts:

```text
channel: pre-release | release
version: release note version choice, without leading v
```

The workflow checks out `source`, resolves current source HEAD to a full
immutable source commit SHA before building, and uses that resolved SHA for the
entire run.

The publish workflow must be dispatched from `source`.

Publishing requires `RELEASE_TOKEN` and `RELEASE_SIGNING_KEY` from the
`release` environment. Do not use the default `github.token` for generated
branch or tag pushes. The workflow checks these secrets before checkout or
payload generation so missing environment configuration fails immediately.

`RELEASE_SIGNING_KEY` is the ASCII-armored private GPG key for the maintainer
release identity. `RELEASE_SIGNING_PASSPHRASE` may be provided when that key is
passphrase-protected. Generated publication commits and release tags must be
signed by this configured maintainer identity rather than authored as
`github-actions[bot]`.

Each publication replaces the selected generated branch with a fresh generated
tree and writes durable branch metadata to:

```text
.github/publication.json
```

The manifest contains:

```json
{
  "channel": "pre-release",
  "version": "1.1.0-beta.2",
  "sourceCommit": "def456...",
  "generatedAt": "2026-07-27T04:00:00Z"
}
```

Do not include the generated branch commit in this manifest. The generated
commit does not exist until after the manifest is committed, and Git already
provides the generated commit identity.

Version tags are signed annotated tags that point to generated publication
commits because those commits are the actual published repository trees.
Provenance is:

```text
tag
generated publication commit
.github/publication.json
sourceCommit
```

Publish creates or replaces generated branch refs, signed annotated git tags,
and GitHub Release records. Publication replacement is destructive for the
selected version. Publish checks for an existing GitHub Release and deletes it,
then checks for and deletes the existing remote tag. This includes draft
releases. Publish then creates and verifies a new signed annotated tag at the
generated publication commit, pushes that tag, and creates a new GitHub Release
with the generated asset. If only the tag exists, only the tag is deleted.
Generated branch replacement does not create tags. `pre-release` uses GitHub's
`Pre-release` label; `release` uses a normal latest release.

After publication, Publish explicitly dispatches the Pages workflow from
`source` with `GITHUB_TOKEN` and `actions: write`. GitHub allows
`workflow_dispatch` events created by `GITHUB_TOKEN`; relying on generated
branch push events is invalid because Pages must only deploy from the
source-owned Pages workflow.

Generated publication payloads are whitelist-built from source-owned inputs.
Source-only authoring surfaces such as `.generated/`, `.vscode/`, `docs/`,
`tools/`, `.gitignore`, `.gitattributes`, `AGENTS.md`, Python caches, and Rust
build output do not appear in pre-release or release branch output.

## Generated Layout

Local generated output lives under `.generated/` with exactly two top-level
sections:

```text
.generated/
  shared/
    pages/
    content/
  repo/
    pre-release/
    release/
```

`shared/pages/` is the built website. It is constructed from `source`.

`shared/content/` is the wiki source used for that website, including localized
content and required assets.

`repo/pre-release/` and `repo/release/` contain the files that would appear on
the generated publication branches. Pages are not authored there; Pages are
constructed by `source`.

Local generated repo payloads also include `.github/publication.json` with local
test versions such as `local-pre-release` and `local-release`.

## Pages Publication View

Pages is built by source-owned tooling and deploys only from the Pages workflow
running on `source`.

The active Pages workflow reads `.github/publication.json` from `release` and
`pre-release`, then checks out the `sourceCommit` values recorded by those
manifests.

The stable release source revision builds the site root. The pre-release source
revision builds `/pre-release/`.

Pages does not merge `pre-release` into `release`, and it does not treat
generated branches as authoring sources. The generated branches identify which
source revisions are current for each publication channel.

Pages validation is owned by `.github/workflows/pages.yml`. Do not add a
separate local Pages test harness. Shared stages should be runnable with the
same commands used by the workflow; GitHub-dependent deployment stages should
skip cleanly outside GitHub.
